# 如何调试寻找内存泄漏（pygamest 生态实操方法论）

> 2026-11-06 · 任务 1 实战产出 · 案例对象 = font_test.py / compute_probe.py
> 泄漏点 = starfish-pygame 纹理 bind 缓存无淘汰（修复 commit starfish fcb84ad）

## 零、适用前提

本文方法论针对 **Rust 侧堆泄漏**（RustPython 嵌入 + wgpu 引擎 + 绑定层），
Windows 桌面开发环境。GPU 显存泄漏、驱动侧泄漏的判读差异见 §五。

## 一、核心思想：先建观测，再谈定位

盲猜泄漏点是最大时间黑洞。正确顺序：

```
① 全局观测（数字说话）→ ② 稳态斜率判定 → ③ A/B 最小化隔离 →
④ 读被隔离路径的源码 → ⑤ 修复 → ⑥ 同一观测复跑验证
```

**原则：每一步都有数字/曲线作为证据，不靠感觉。**

## 二、观测基建：计数分配器 + RSS 采样（本仓已内置）

### 2.1 工具（pygamest-dev/src/leak_harness.rs）

- `CountingAlloc` 全局分配器：16B 头存 [回退距离, 用户尺寸]——
  活分配数/活字节**精确**统计（任意对齐安全）
- RSS 采样（GetProcessMemoryInfo）
- `PYGAMEST_MEMTRACE=1` 开监控线程（3s 一拍）：

```
[memtrace] t=30s live_alloc=109079 live_bytes=51.1MB total_alloc=893.8MB rss=532.8MB
```

### 2.2 判读

| 观测 | 结论 |
|---|---|
| `live_alloc` 稳态循环内**线性涨** | Rust 堆泄漏实锤（斜率 ÷ 帧率 = 泄漏量/帧） |
| `live_alloc` 平 + RSS 涨 | GPU 显存/驱动侧（wgpu 资源未释放或驱动缓存） |
| 都平 | 无泄漏（缓存型增长会到平台期后走平） |

### 2.3 使用

```bash
cargo build --release -p pygamest-dev
PYGAMEST_MEMTRACE=1 ./target/release/python.exe examples/xxx.py
```

（分配器计数从进程启动即生效；监控线程只负责打印。）

## 三、A/B 最小化隔离法（本案锁定的关键一击）

**构造一对只差一个变量的最小脚本**，对照曲线：

```
leak_a_newtex.py  每帧 font.render 新 Surface（新纹理）+ draw_surface
leak_b_sametex.py 同一 Surface 复用（纹理只建一次）
```

实测结果：

| | live_alloc @6s | @18s | @30s | 结论 |
|---|---|---|---|---|
| A 新纹理 | 42919 | 75981 | 109032 | 线性涨 ~2771/s |
| B 复用 | 27790 | 27791 | 27791 | **完全走平** |

→ 泄漏在"每帧新纹理"路径，与字体/事件/主循环无关。

**隔离脚本设计要点**：
- 变量唯一（只差怀疑的那个调用）
- 循环够长（跨过缓存上限/平台期）
- 去掉一切非必要路径（egui、compute、文本上屏……每个变量单独一脚本）
- 断言用区间不用精确值（带缩放/外扩语义的路径）

## 四、本案泄漏点与修复

**泄漏链**：字体每帧 render → 新 Surface → 新 `Texture`（新 id）→
绘制时进 `Gpu.binds` 纹理 bind 缓存（`HashMap<usize, BindGroup>`）
→ BindGroup 持 `TextureView` Arc → **纹理永活**，缓存无淘汰 → 无界增长。

**修复**：bind 缓存加容量上限（4096）+ FIFO 淘汰（`bind_order` VecDeque
同步维护；被逐 = BindGroup 释放 → View→纹理引用链断 → 纹理可回收；
被逐纹理再用时重建，builder 廉价）。

**验证曲线**（leak_a 越过上限后）：

```
t=36s live_alloc=122006  ← 到达 4096 上限
t=48s live_alloc=122023  ← 精确走平（插入/淘汰平衡）
t=72s live_alloc=122006
```

font_test / compute_probe 复跑同样平台期 ✓。

## 五、扩展判读（本仓未发生但会遇到的形态）

| 形态 | 特征 | 手段 |
|---|---|---|
| GPU 显存泄漏 | live 平、RSS/显存涨 | wgpu 资源计数（device poll + 资源审计）或逐路径注释复跑 |
| Python 侧引用环 | live 涨、对象都在 VM 内 | gc 模块 + `gc.get_objects()` 分型统计（RustPython gc 支持） |
| wasm 泄漏 | 浏览器 DevTools Memory 快照对比 | heap snapshot diff（三次快照找增长类） |
| 间歇泄漏 | 稳态平、特定操作后跳 | 操作日志 + 操作前后采样配对 |

## 六、工具箱备忘（各手段适用性）

| 手段 | 平台 | 优点 | 局限 |
|---|---|---|---|
| 计数分配器（本仓） | 全平台 | 精确活量、零依赖、可长跑 | 只见 Rust 堆 |
| RSS 采样 | win/linux | 总量视角（含驱动） | 粗粒度 |
| Valgrind massif | linux | 精确调用栈分配曲线 | Windows 不可用、慢 20-50× |
| ASan/LSan | win(nightly)/linux | 精确泄漏栈 | 工具链复杂、误报需滤 |
| Windows UMDH/heap snapshot | win | 原生栈级 | 需符号与 gflags 配置 |

**本仓结论：计数分配器 + A/B 隔离**是性价比最高的组合——本案全程未出
Windows，约 40 分钟定位到修复。
